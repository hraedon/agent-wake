## On the project

agent-wake is in a solid state for its v1 daemon architecture. The unix-socket protocol between daemon and adapters is well-specified (proto.py validates frames, hello handshake has versioning). The daemon's config validation is thorough — mutual exclusion of secret forms, URI scheme validation, vault block completeness. The opencode adapter's label-based routing with self-registration tools is an elegant design that avoids the need for central routing config.

The main architectural tension is that the daemon's heartbeat (30s ping interval) will kill adapters that are legitimately busy processing long model turns. This is a real problem for any non-trivial agent interaction. The daemon also lacks graceful degradation when an adapter disconnects mid-delivery — `send_frame` throws `ConnectionResetError` that propagates all the way to the HTTP handler, returning 500 to the sender.

The test coverage is strong overall (~240 tests across three test suites), but the Claude adapter has two untested modules (channel.py, _notify.py) and the opencode plugin entry point (index.ts) has no tests for its lifecycle logic.

## On the work done

All six fixes were straightforward — the breadcrumbs were well-described with exact file/line references, which made them quick to resolve. The opencode backoff fix (5s minimum retry interval) is conservative and won't affect normal startup. The SSRF validation in outbox.py only covers scheme enforcement for now; BC-WAKE-009 tracks the remaining IP-level blocking.

I'm confident in all the changes. The one thing I'd flag: the `permission.py` behavior validation uses `ValueError` which the caller (the verdict HTTP handler) may or may not catch gracefully — depends on how Flask/aiohttp routes the exception. This should be verified in the Claude adapter's server.py error handling.

Items 4 and 5 are the biggest adoption blockers — without a quickstart, new users can't get started in under 5 minutes.
