## On the project

agent-wake is in a genuinely good shape for its role as the suite's Tier 2 signaling component. The Plan 004 suite-cohesion work (doctor, install-harness, Dockerfile, Windows Service) that landed in the prior session was solid scaffolding; this session was the polish round that made it actually deployable rather than just present.

The thing that struck me working in the code: the daemon's ingest → gating → router → socket_server pipeline is clean and well-tested, but the *edges* where it meets the outside world (HTTP bind address, env-var overrides, version negotiation) had accumulated small gaps that none of the existing tests caught. The silent-wrap-of-unknown-v bug (BC-010) is the canonical example: the schema says MUST reject, the test suite had happy-path coverage, but the actual rejection logic was a single `==` comparison that failed open in three different ways (no event_id bypass, bool/float sneaking through `== 0`, and the wrap fallback). This is the kind of thing adversarial review exists for.

The suite blueprint (`/projects/agent-suite-blueprint.md`) is a genuinely well-constructed strategy document. The four contracts (config, compatibility matrix, bootstrap order, health) are the right abstractions, and reading it after having worked in three of the six components now, the cohesion story holds together. agent-wake's contribution to that story — doctor JSON, install-harness, suite.env reading — is now real rather than aspirational.

## On the work done

**What went well:**
- The BC-010 fix is the most important change. The first version I wrote was incomplete (only rejected when `event_id` was present) and both reviewers caught it independently — that's exactly the value of running two reviewers. The strict type check (`isinstance(version, bool)` exclusion) came from GLM and is the kind of Python gotcha that's easy to miss.
- Centralizing listen resolution in `resolve_listen()` and having both `main._run()` and `doctor._check_ingress_reachable()` use it eliminated a real operability gap that Kimi flagged — doctor would have probed the wrong port when the daemon used an env override. Extracting the helper was cleaner than duplicating the logic.
- The done_callback on the SIGHUP refresh task was a small fix but addresses a real silent-failure mode. Distinguishing `CancelledError` (GLM's finding) from real failures matters because the callback fires on shutdown too.

**What I'm confident in:**
- The BC-010 rejection logic and its 5-test coverage (int v=1, no-event_id bypass, bool, float, string).
- The loopback detection via `ipaddress` — covers the full 127.0.0.0/8 range and IPv6 ::1 correctly, which the original `_LOOPBACK_HOSTS` set missed.
- The port env validation raising `ConfigError` instead of crashing.

**What I'd want a second pair of eyes on:**
- The `_warn_non_loopback_bind` ERROR branch is effectively unreachable in production because `load_config()` already enforces that every source has a `secret_uris` list. GLM flagged this correctly. I kept the defensive check (belt-and-suspenders for configs built outside `load_config`, e.g. tests), but it means the most dramatic-sounding security warning will essentially never fire through the normal path. The WARN branch (authenticated + non-loopback) is the one that actually fires in containers. This is honest but the function's docstring could be clearer that the ERROR path is defensive.
- The `AGENT_WAKE_OPENCODE_PLUGIN` env override now validates `.js` + is_file, but a hostile env can still point at an arbitrary `.js` file on disk. In a single-operator OSS tool this is acceptable (the operator controls their own env), but if agent-wake ever runs in a shared CI context this becomes a prompt-injection vector. Worth a note in the install-harness docs when they're written.

**What was awkward:**
- Trying to resolve BC-010 in agent-notes hit a pending regista migration (schema `agent_wake` is at 37, needs 38). I left the breadcrumb open and noted it here rather than running a migration that's out of scope for this session. The next session should run `regista migrations` for the agent-wake schema and then close BC-010 (and BC-002 partial) via the CLI.
- The Dockerfile sets `AGENT_WAKE_LISTEN_HOST=0.0.0.0` via ENV, which means the non-loopback warning fires as WARN on every container start. That's correct behavior (the operator opted in via the image's ENV), but it means container logs will always carry one WARNING line. Operators who grep for warnings should be aware.
