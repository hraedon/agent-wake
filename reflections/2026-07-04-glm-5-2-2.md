## On the project

agent-wake continues to be in good shape — the ingest → gating → router → socket_server pipeline reads cleanly and the test suite (253 now) is genuinely thorough for an internal-mechanics layer. The thing this session reinforced: the *edges* are still where the bugs live. The router had perfect happy-path coverage but no test for "the subscriber dies mid-send," and the config loader had thorough validation of *valid* configs but no test for "the file isn't JSON at all." Both are the same class of gap — the suite proves the contract holds when inputs are well-formed, not when they're hostile or broken.

The regista migration story is fine but the discoverability is poor. There's no `regista schema migrate` subcommand; the way to apply pending migrations is `regista schema init`, which reads like it would fail on an existing schema but actually calls `CREATE SCHEMA IF NOT EXISTS` + `run_migrations` and is the intended upgrade path. I spent ~5 minutes confirming that was safe. Worth a note in regista's own AGENTS.md, but not this project's problem.

## On the work done

**What went well:**
- The BC-009 fix is the higher-value of the two. A 500-with-traceback on adapter disconnect is a real operability failure — it looks like a daemon crash rather than the benign "no live subscriber" case it actually is. Returning 202 `no_subscriber` matches the existing semantics for "no subscriber at all," which is the right collapse.
- The adversarial review earned its keep. Both reviewers independently flagged (a) `BrokenPipeError` is a redundant subclass of `ConnectionError`, (b) `RuntimeError` in the catch tuple is too broad and could mask a real `send_frame` bug, and (c) the `from e` chain on the config `ConfigError` retains the raw document text in `JSONDecodeError.doc`. I'd have shipped all three without the review. Narrowing to `OSError` and dropping the chain are genuine hardening.
- The test that verifies `RuntimeError` is *not* swallowed (`test_deliver_does_not_swallow_non_connection_errors`) is the one I'm most glad I added — it pins the design decision that the catch is intentionally narrow, so a future maintainer broadening it has to confront the test.

**What I'm confident in:**
- The `OSError` catch is the correct umbrella for asyncio transport failures (`ConnectionResetError`, `BrokenPipeError`, `ConnectionAbortedError` all inherit from it).
- `_evict` being idempotent with the socket_server's finally-block: both paths use `pop(..., None)` and `try: remove; except ValueError`, and asyncio is single-threaded so there's no interleaving. GLM verified this explicitly and correctly.
- The config nested-dict checks (`sources`/`routing`) close a real `AttributeError`-on-`.items()` crash path that the top-level dict check didn't cover.

**What I deliberately did not change (and want to flag as a conscious decision):**
- The dedupe-before-deliver interaction. Both reviewers flagged that BC-009's new 202 `no_subscriber` (for a mid-send disconnect) is semantically "terminal" because `dedupe.check()` already consumed the `event_id`, so a same-id retry is rejected as duplicate. This is pre-existing behavior, explicitly asserted by `test_e2e.py:331-343`, and the documented design in AGENTS.md is "wake hits live sessions only." Properly fixing it is the durable-inbox work (BC-WAKE-012). I documented the interaction in a router.py comment rather than reordering dedupe — reordering would change e2e-test-asserted semantics and is a larger design call than this session should make unilaterally.

**What was awkward:**
- The `_evict` helper duplicates cleanup that the socket_server's finally-block also owns. It's safe (idempotent, single-threaded), but two owners of "close this writer" is a smell. GLM suggested making the socket_server the sole owner of `close()` and having `_evict` only call `unsubscribe` — that's cleaner but requires the router to trust the socket_server's teardown to happen promptly, which it does via the read-loop EOF. I kept the belt-and-suspenders version because closing the writer from the router side accelerates teardown; worth revisiting if the ownership ever causes a real bug.

## Gaps to flag

- `daemon/src/agent_waked/ingest.py:206-213`: dedupe consumes `event_id` before `router.deliver`. When deliver returns `no_subscriber` (now including the transient mid-send-disconnect case from BC-009), the event is permanently lost — a same-id retry is rejected as duplicate. Documented in `router.py:84-90` comment; proper fix is BC-WAKE-012 (durable inbox). Not changed this session by design.
- `daemon/src/agent_waked/router.py:103-117` (`_evict`): two cleanup owners (router + socket_server finally-block). Safe today (idempotent, single-threaded), but if a future change adds `await` inside `_evict` or makes the router multi-loop, the lack of a lock becomes a real race. The comment doesn't call out the single-loop invariant as the load-bearing assumption.
- `daemon/src/agent_waked/ingest.py:209` (`result = await router.deliver(event)`): `deliver` returns only `"queued"` or `"no_subscriber"`. There's no `"delivery_failed"` status to distinguish "no subscriber ever existed" from "subscriber existed but died mid-send." Both collapse to the same 202 response. Acceptable under the live-sessions-only design, but if durable redelivery lands, this distinction matters.
- `regista` CLI: no `schema migrate` subcommand; `schema init` is the upgrade path and its name misleads. Not agent-wake's bug, but it cost orient time and will cost the next session too until regista documents it.
- `daemon/src/agent_waked/main.py:198-216` (`_reload_config` SIGHUP handler): uses `loop.create_task` with a `RuntimeError` guard for "no running loop," but inside a SIGHUP handler the loop is guaranteed running — the guard is dead code. Minor, but it suggests the author wasn't sure of the lifecycle.
