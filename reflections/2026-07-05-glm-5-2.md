## On the project

agent-wake's publication-gate infrastructure is well-scaffolded — the gpo-lens-borrowed scanner, the layered denylist resolution (local file / env var / CI secret), and the pre-commit hook are all in place. The gap was that the denylist had no patterns configured, so the gate was a no-op. Now it has 17 patterns covering all identifier forms from the sibling repos' samples, and the gate passes clean on the current tree.

The filter-repo audit result (zero leaks) is a relief — it means no history scrub is needed, which avoids the adcs-lens WI-010 pain (delete-and-recreate to purge pushed PR refs). But it's also slightly surprising given how much work-domain context flows through reflections and design docs in this project family. The discipline of keeping samples gitignored and using synthetic placeholders in committed fixtures is paying off.

## On the work done

The adversarial review earned its keep decisively. Both reviewers independently found the critical bug: the updated `docs/publication-gate.md` contained a table with every literal identifier value, which meant the identifier gate would flag its own checklist document — 20 violations on a single file. The first reviewer (Kimi) also flagged a username token as potentially fabricated because they couldn't run grep to verify it in the adcs-lens samples (it IS there, in the org-specific CA template's ACE list). The second reviewer (Nemotron) correctly identified the branch count discrepancy (5 feature + 1 rename, not 6+1) and the stale Plan 004 ground-truth paragraph.

The fix for the self-flagging bug was straightforward but instructive: the checklist now describes identifier categories (e.g., "AD domain name (DNS form)") without repeating the literal values. The values live only in the gitignored denylist file. This is the right design — a committed document should never contain the identifiers it's trying to prevent.

I'm confident in the denylist coverage and the audit result. The filter-repo dry-run with `--replace-text` showed zero content changes, and a direct grep of all blobs and commit messages confirmed zero matches. The one area I'd want a second look at is the lab-domain short-name token — at 5 chars it's the shortest in the denylist and could theoretically cause false positives, though it's specific enough that it's unlikely in this repo's context.

## Gaps to flag

- **No unit tests for `scripts/check_committed_identifiers.py`.** The scanner is the hard gate and has zero tests. gpo-lens ships `tests/test_check_identifiers.py` with 16 tests that should be ported. `scripts/check_committed_identifiers.py` is load-bearing and untested.
- **The CI identifier-gate job passes vacuously when the secret is unset.** `check_committed_identifiers.py:179-185` exits 0 with a "skipping" message. This is correct for a fresh clone (fail-open) but means the CI gate shows green without scanning anything until the owner sets the secret. The CI job should detect `GITHUB_ACTIONS=true` and fail if the secret is missing.
- **The multi-word identifier gap is real.** The display-name form of the CA template (with spaces) cannot be denylisted because the parser splits on whitespace. The no-space form covers the programmatic `name` field, but a reflection or doc that uses the display name with spaces would pass the gate.
- **`_SKIP_DIRS` in the scanner includes `samples`** which agent-wake doesn't have. Vestigial from gpo-lens. Harmless but worth noting if agent-wake ever grows a `samples/` directory that should be scanned.
- **The `replacements.txt` for filter-repo is ephemeral.** I generated it in `/tmp` and deleted it after the audit. The checklist documents how to regenerate it from the denylist, but there's no committed generator script. If the owner needs to run the real scrub later, they'll need to recreate it.
