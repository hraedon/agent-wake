# Session Reflection — 2026-05-26

**Work summary:** Implemented phases 3 and 4 of the v1 daemon spec. Phase 3 adds the `Outbox` class to the daemon for outbound reply delivery (POST v0 reply objects to per-source callback URLs, 30s timeout, no retries). Phase 4 slims the Claude adapter into a thin daemon client: deleted `ingest.py` and `gating.py`, added `client.py` with unix-socket connection management, `ReplyResultBus` for cross-thread reply result delivery, and rewired `reply.py` to delegate through the daemon instead of making direct HTTPS calls.

---

## On the project

The spec is unusually precise for a project at this stage — every field, frame type, status code, and error mapping is nailed down before implementation. That made implementation mechanical (in a good way). The phase plan is well-sequenced: each phase builds cleanly on the last with no backtracking needed.

The two-repo split (daemon + adapter) with a shared config file is a pragmatic choice. The adapter being dependency-free (stdlib only) is a nice property that's worth preserving. The unix-socket wire protocol is simple enough that a future adapter for another harness can be written in an afternoon.

One thing that feels slightly off: the adapter's `__main__.py` now runs asyncio in the main thread and the synchronous MCP server in a daemon thread. This works but means stdin/stdout are shared between two threads (MCP reads stdin, channel emits write stdout via `_notify.py`'s lock). It's thread-safe today because `_notify.py` uses a lock, but it's a pattern that could bite if someone adds more stdout writes without the lock.

## On the work done

Phase 3 was straightforward — the `Outbox` class is a thin wrapper around `aiohttp.ClientSession`. One hiccup: `asyncio.TimeoutError` stringifies to `""` in Python, which meant the error message in `reply_result` was empty. Fixed by special-casing `asyncio.TimeoutError` to produce `"callback timed out"`. The 30-second timeout test takes ~30s to run, which bloats test time. Not much to be done about that without mocking time.

Phase 4 was more involved due to the cross-thread communication between the sync MCP handler and the async daemon client. The `ReplyResultBus` uses `threading.Event` + a shared dict keyed by `reply_id` — simple and correct for this use case. The `send_reply_frame` function uses `asyncio.run_coroutine_threadsafe` to bridge the synchronous MCP thread to the async event loop. This is the standard pattern and should be robust.

Dropping `ulid-py` from the adapter and using `uuid.uuid4()` for `reply_id` is a minor deviation from the spec's "ULID" language, but the spec also says "no new dependencies" and the daemon's proto validation only checks that `reply_id` is a string. Functionally equivalent.

## Gaps to flag

- **`asyncio.TimeoutError` empty stringify.** Fixed in outbox.py with an explicit isinstance check, but this is a Python footgun worth knowing about. `daemon/src/agent_waked/outbox.py:101-107`.
- **`__main__.py` thread model documentation.** The adapter's main-thread-asyncio + daemon-thread-MCP pattern isn't documented anywhere in the code. A future contributor might not realize `_notify.py`'s lock is load-bearing. `adapters/claude/src/agent_wake_claude/__main__.py:30-42`.
- **`demo.sh` still references old v0 standalone model.** `adapters/claude/examples/demo.sh` generates a v0 config and curls `localhost:8788` directly — it doesn't mention the daemon. Will need updating in phase 5/6 when the top-level README is rewritten.
- **No adapter test for `reply_id` format.** The spec says ULID but we use UUID4. The daemon accepts any string. No test verifies the exact shape — only that it's a non-empty string. Low risk but worth noting.
