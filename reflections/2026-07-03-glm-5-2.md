## On the project

agent-wake has a clean, well-structured daemon codebase. The separation between config, ingest, router, socket_server, and secrets is good — each module has a clear responsibility and the blast radius of changes is small. The test suite (215 tests) is thorough for the happy paths.

The project sits at an interesting maturity point: the daemon is solid, adapters work, but the suite cohesion layer (doctor, install-harness, suite.env) is the thing that turns it from "a tool you install" into "a suite component." Plan 004 is the right next step — it's the glue that makes agent-wake deployable as part of the agent-suite without hand-editing.

The suite blueprint (`/projects/agent-suite-blueprint.md`) is a genuinely well-thought-out strategy document. The four contracts (config, compatibility matrix, bootstrap order, health) are the right abstraction. The install-harness contract doc is clear and prescriptive, which made implementation straightforward.

## On the work done

**What went well:**
- The suite_config module was straightforward — the precedence chain is clean and the env-file parser handles the common cases.
- The install-harness contract doc was prescriptive enough that implementation was mostly mechanical. The idempotency, dry-run, and uninstall patterns followed naturally.
- The adversarial review caught real bugs: the `_find_opencode_plugin_path` parents index bug (off-by-one between `parents[3]` and `parents[4]`), the KeyError crashes in uninstall when config was manually edited, the Windows signal handler incompatibility, and the silent JSON corruption data loss path.
- Running two adversarial reviewers in parallel (Kimi + GLM) was efficient — they found overlapping issues with different emphasis, giving good coverage.

**What I'd want a second pair of eyes on:**
- The Windows Service wrapper is scaffolding — it compiles but has never run on Windows. The signal handler fix (guarding `add_signal_handler` with try/except) is correct in principle but untested on ProactorEventLoop. The `_run()` function's SIGHUP handler is silently skipped on Windows, which means config reload doesn't work on Windows — that should be documented.
- The `doctor --json` shape includes `degraded` which isn't in the bootstrap-contract example. The agent-suite doctor aggregator handles it (it checks `data.get("degraded", False)`), but if a stricter aggregator is built later, this could be rejected.
- The `regista.chain_ok` field is `None` because agent-wake doesn't sign events — it's a pass-through component. This is semantically correct but might confuse a suite-doctor that expects a boolean.

**What was awkward:**
- The CLI refactoring (extracting `_build_secrets_parser` from the main `build_parser`) required adding `from __future__ import annotations` to `secrets.py` because `argparse._SubParsersAction` isn't subscriptable at runtime in Python 3.11. This is a known Python argparse typing quirk.
- The manifest tracking for install-harness is a sidecar file approach. It works, but if the manifest gets out of sync with the actual harness config (user manually edits settings.json), uninstall won't find the keys. The contract allows this approach but a sentinel-based approach might be more robust.

## Gaps to flag

- `daemon/windows_service.py`: The `_run()` function's SIGHUP config-reload is silently skipped on Windows (the `add_signal_handler` call fails and is caught). Config reload doesn't work on Windows — this should be documented as a known limitation.
- `daemon/src/agent_waked/cli/install_harness.py`: The `_find_opencode_plugin_path` fallback path (`~/.local/share/agent-wake/opencode/dist/index.js`) is never populated by any install step. If the source tree path doesn't match (e.g., pip-installed without source), the opencode install will fail.
- `daemon/src/agent_waked/doctor.py`: The `_check_adapters_installed` check uses `bun` on PATH as a proxy for "opencode plugin built." `bun` being installed doesn't mean the plugin is built (`dist/index.js` exists). A more precise check would mirror `_find_opencode_plugin_path()`.
- `daemon/Dockerfile`: The daemon binds to `127.0.0.1` by default inside the container, so `docker run -p 0.0.0.0:8788:8788` won't work — the host can't reach the container's loopback. This should be documented or the default config should use `0.0.0.0` in container mode.
- The existing open breadcrumbs (BC-002, BC-004, BC-005, BC-009, BC-010, BC-011, BC-013) are all still open. Plan 004 didn't address them — they're Plan 003's reliability work.
- `daemon/src/agent_waked/main.py`: The `_reload_config` function uses `loop.create_task(resolver.refresh_all())` but never awaits or tracks the task. If the task fails, the error is swallowed. This is a pre-existing issue, not introduced by Plan 004.
