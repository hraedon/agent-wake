## On the project

agent-wake is a clean, narrow-scope project: one event schema, two harness adapters, no state. The v0 spec in `design/v0-implementation-plan.md` is unusually concrete — it prescribes file layouts, headers, exact response bodies — which made implementation straightforward but also rigid. The biggest tension I felt was between "use the official MCP Python SDK" and "the SDK doesn't expose custom notification methods (notifications/claude/channel)". I ended up hand-rolling raw JSON-RPC over stdio, same pattern as the wake-probe reference. This is the right call for v0 because it works today, but it means `pyproject.toml` declares a dependency on `modelcontextprotocol` that the adapter doesn't actually import. That dependency should either be removed or the adapter should migrate to the SDK once channel notifications are supported.

The opencode side is simpler because the plugin runs in-process and calls `client.session.prompt()` directly. The TypeScript adapter is thinner and feels more aligned with its harness's native model.

## On the work done

What went well:
- Ingest logic (pass-through vs. wrapping, dedupe window, HMAC gating) is tested and solid.
- `fakechat-test.py` is a real end-to-end test: it spawns the adapter, completes MCP initialization, POSTs a wake event, and asserts on the stdout notification. That's real coverage for the critical path.
- The `_Callback` wrapper in `ingest.py` was a subtle but important fix to avoid Python's implicit `self` binding on callable class attributes.

What I'm unsure about:
- The permission relay implementation is minimal (in-memory `_pending` dict, no timeout, no cleanup). It's enough for v0 but will leak entries if verdicts never arrive.
- `reply.py` loads config fresh on every tool call because `_cached_config` isn't used there. Not a correctness issue, just unnecessary I/O.
- opencode adapter is skeletal: no custom tool registration for replies yet, and `reply.ts` uses `fetch` fire-and-forget without awaiting the response body. The spec says "best-effort in v0" so this is acceptable, but it's under-exercised compared to the Claude side.

## On what remains

## Gaps to flag

- `adapters/claude/src/agent_wake_claude/server.py:14` — imports `send` from `_notify`, but `_notify` writes to `sys.stdout` with a thread lock. This is fine for single-threaded stdio but could deadlock if a notification handler is ever called from a thread that already holds the lock. Low probability in v0, worth noting.
- `adapters/claude/src/agent_wake_claude/config.py:25` — `_cached_config` is never invalidated. If the user edits their config file while the adapter is running, changes are ignored until restart. Acceptable for v0 but should be documented.
- `adapters/claude/src/agent_wake_claude/permission.py:26` — `_pending_verdicts` grows unboundedly if permission requests are received but no verdicts are POSTed back. No TTL or eviction.
- `adapters/opencode/src/ingest.ts:48` — `isDuplicate` and `recentEventIds` are module-level globals with no locking. Concurrent requests under Bun could race. Bun's event loop is single-threaded so this is probably fine, but it's a latent concurrency hazard if the ingest handler ever uses Workers.
- `tools/fakechat-test.py` uses a fixed `time.sleep(0.5)` for the HTTP listener startup. On slow machines this may flake. A readiness probe (retry-connect loop) would be more robust.
